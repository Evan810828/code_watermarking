\section{Research question and measured scope}

The study measures the detection and functional correctness of existing
watermarking methods on HumanEval, the MBPP test split, and the LiveCodeBench
release-v1 code-generation test split. The methods are KGW, SemStamp, SWEET,
CodeWM, and SeqMark. The tables preserve existing measurements. They do not
establish a new watermark method or a cross-dataset winner.

The full splits contain 164, 500, and 400 tasks, respectively. Several CodeWM
runs cover only subsets. SeqMark has complete HumanEval and MBPP evaluations
for two encoders; its LiveCodeBench execution was cancelled and contributes
no complete benchmark result. Partial and superseded executions remain
available as historical evidence.

\section{Methods and experimental conventions}

KGW biases a context-seeded token green list. SWEET applies a green-list bias
at positions exceeding an entropy threshold. SemStamp rejection-samples
line segments using keyed regions of sentence embeddings. CodeWM learns a
context-dependent token pairing and an embedding switch. SeqMark applies
mean-centred semantic rejection sampling to the complete extracted program,
which is treated as one sequence. The SeqMark detector reuses the saved
generation centre for both watermarked and unwatermarked programs.

The shared model in the main comparison is Qwen3.5-4B. KGW, SemStamp, SWEET,
and the CodeWM chat runs use temperature $0.7$, nucleus probability $0.8$,
top-$k=20$, a 2000-token generation budget, and random seed 42. Thinking is
disabled. Dataset-level prompts request Python without comments or docstrings.
KGW and SWEET use green fraction $0.5$ and bias $8$. SemStamp uses line
segmentation. CodeWM is measured at biases $2$ and $8$ with switch threshold
$0.7$ in the Qwen comparison. Its original-paper reproduction is separate.

SeqMark uses temperature $1.2$ for centre samples, candidate programs, and
paired controls, unrestricted nucleus sampling, disabled top-$k$, repetition
penalty $1.05$, 50 centre samples, and at most 50 rejection trials. A search
over 100 MBPP training tasks selected five hash dimensions and green fraction
$0.1$. The same configuration applies to Gemma and SBERT on both test splits.
Those training tasks are disjoint from the MBPP test split; HumanEval does
not select the parameters. Gemma denotes the embeddinggemma-300m encoder;
SBERT denotes the SemStamp sentence encoder. Their native tokenization,
pooling, and truncation remain part of the encoder comparison.

These sampling and implementation differences are experimental conditions,
so the five-method table is not a controlled comparison varying only the
watermark algorithm. Every run uses one recorded generation seed; the tables
do not estimate variation over independent seeds.

\section{Evaluation protocol}

Detection receives the extracted Python program. The positive class contains
watermarked programs; the negative class contains paired unwatermarked model
generations. Extraction failures are unscoreable. A method can also return a
null detector score after successful extraction, so scored and unscoreable
counts need not sum to the task count.

For target false-positive rate $q$, the reported operating point is
\[
\operatorname{TPR}_{q}=\max_{t:\operatorname{FPR}(t)\le q}
\operatorname{TPR}(t),\qquad \text{positive if } z\ge t.
\]
This definition selects the best attainable deterministic threshold under
the false-positive constraint. Equal scores remain together. The calculation
uses no interpolation or randomized tie splitting. Positive and negative
rates use their respective scoreable-class denominators. AUROC denotes the
area under the receiver operating characteristic curve.

Functional evaluation uses the benchmark's saved code extraction and retains
the task cohort independently of detector scoreability. The chat-protocol
pass@1 values use one generated program per task. LiveCodeBench evaluation
uses the recorded cap of 20 tests per task, with inputs larger than 10 MB
excluded during test preparation. The original-paper CodeWM protocol instead
estimates pass@1 from 20 completions and detects the first valid completion.

cohort and generation configuration.

SeqMark has a discrete per-program score. Its accepted-score group may exceed
a low false-positive budget, causing zero attainable true-positive rate at
that budget even when AUROC is high. The report separately retains the
training-selected classification threshold, its precision and recall, and
the full empirical receiver operating characteristic. Those quantities do
not replace the deterministic fixed-FPR columns.

\section{Limitations}

The measurements retain their original generation settings and task cohorts.
Capped CodeWM cells and cancelled SeqMark LiveCodeBench executions do not
supply missing full-split measurements. Scoreable-subset detection cannot be
interpreted without the extraction and null-score counts. Different prompting,
quality estimators, sampling, and model families prevent pooling the
original-paper reproduction, the first round, and the main comparison.
No new benchmark execution or method-selection criterion is introduced by
this report.
